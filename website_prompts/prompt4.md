Now build the ApexRN documentation experience.

The documentation should take inspiration from the INFORMATION ARCHITECTURE and developer experience of shadcn/ui.

Do NOT copy shadcn's visual design.

ApexRN should retain its own refined brutalist identity.

==================================================
DOCUMENTATION GOAL
==================

A developer should be able to:

1. understand ApexRN
2. install it
3. find a component
4. see it working
5. understand its props
6. copy usage code
7. understand variants
8. understand composition
9. troubleshoot common issues

with minimal friction.

==================================================
ROUTES
======

Create a sensible structure, statically generated by Next.js (`output: 'export'` — every route below is prerendered at build time, no server):

/docs
/docs/installation
/docs/introduction
/docs/theming
/docs/components
/docs/components/[component]

Use `generateStaticParams` (or the App Router static-export equivalent) driven by the real registry (`registry/public/index.json`) so a route only exists for a component that actually ships. Never a hardcoded list that can drift from the registry.

==================================================
DOCS SIDEBAR
============

Create a persistent documentation sidebar.

Organize components into logical categories based on the ACTUAL library (check `registry/meta.json` / `docs/components.md` groupings — Actions, Display, Feedback, Forms, Overlays, Navigation, or whatever the real grouping is).

Only create categories that make sense from the real component inventory.

Do not invent components.

==================================================

Related components

==================================================
LIVE PREVIEWS — VIA THE EMBEDDED LAB
=====================================

This is critical.

Do not show screenshots.

Do not mount `@apexrn/ui` directly in this Next.js app (`website/` has no react-native-web/Reanimated dependency — see `instructions.md`).

Instead, embed the `demo/` Lab's web export as an `<iframe>` in chrome-less embed mode, hash-routed to this component's specimen (`?embed=1#<component>:<theme>`).

Where appropriate provide, as ordinary Next.js controls OUTSIDE the iframe, that post messages INTO it:

- variant selector
- size selector
- state selector
- theme selector (`postMessage({ type: 'apexrn:theme', mode })`)
- relevant props (`postMessage({ type: 'apexrn:tokens', ... })` for token-level, or a specimen-specific message shape agreed with the Lab's embed-mode handler)

The preview should update live via the message round-trip. Debounce rapid control changes so the iframe isn't flooded.

Show a "Known limits" note near the preview: this is a web render via react-native-web inside the Lab; haptics, native `Modal` window behavior, and some native gestures differ on an actual device.

==================================================
CODE
====

Every example should have:

- syntax highlighting
- copy button
- correct TypeScript
- correct imports
- real props
- actual API

Never fabricate code. Generate examples from `docs/components.md` snippets and/or the real component API — never hand-write a duplicate that can drift.

==================================================
DESIGN
======

The docs should feel:

clean
fast
technical
focused

Use ApexRN's visual language but reduce the visual noise compared with the landing page.

Think:

shadcn information architecture
− ApexRN visual identity.

==================================================
SEARCH
======

Implement documentation search as a static, client-side index built at compile time (e.g. Pagefind) over the generated static pages — no backend, consistent with `output: 'export'`.

Search should find:

- components
- documentation pages
- relevant headings

Keyboard navigation should work.

Provide a familiar command-style search experience if appropriate.

==================================================
NAVIGATION
==========

Include:

- previous/next component navigation
- breadcrumbs where useful
- active sidebar state
- mobile navigation
- table of contents for long pages

==================================================
MOBILE
======

Documentation must work properly on mobile.

Do not simply collapse the desktop sidebar.

Create an intentional mobile documentation experience.

==================================================
AEO/SEO
=======

Alongside each component page's HTML, generate a plain-Markdown mirror (e.g. `/docs/components/<name>/llms.txt` or a sitewide `/llms.txt` index) containing: real name, real props, real usage snippet — generated from the same source data as the HTML page, never authored separately. This is for AI agents/crawlers that prefer fetching plain text directly.

Keep all prose, props tables, and code blocks as real static HTML text — never render them only inside the iframe, where crawlers can't see them.

==================================================
VALIDATION
==========

Every documentation page must:

- build (static export)
- render
- have working examples
- have valid links
- embed the real component via the Lab iframe (never a fake HTML replacement)
- have correct code
- have no placeholder content
- have a corresponding registry entry (build fails otherwise)
